## Recommended standard codes and treatment

### 1. `Bangladesh`

- **Recommended standard code:** `BGD`  
- **Geo type:** Country  
- **Mapping:** Direct, high confidence.  
- **Note:** This is the canonical name; map 1:1 to ISO3 `BGD`.

<hr>

### 2. `Bangladesh (excl. EPZ)`

- **Recommended standard code:** `BGD`  
- **Geo type:** Country (with qualifier)  
- **Mapping strategy:**
  - For most macro/trade‑openness uses, this is still essentially **national Bangladesh** with a methodological qualifier (excluding Export Processing Zones).
  - Map to `BGD`, and keep the qualifier in a **separate metadata field**, e.g.:
    - `geo_code = 'BGD'`  
    - `geo_note = 'Excludes EPZ'` or `coverage = 'national_excl_EPZ'`
- **When to treat differently:**
  - Only if your analysis explicitly needs to distinguish “including EPZ” vs “excluding EPZ” series. In that case, you might:
    - Use `BGD` as the base code and add an extra dimension (e.g., `coverage_type`), rather than inventing a new geographic code.

<hr>

### 3. `South Asia (developing only)`

- **There is no single standard World Bank code that exactly means this.**  
- **Closest standard concept:** World Bank region `SAS` = “South Asia” (includes Afghanistan, Bangladesh, Bhutan, India, Maldives, Nepal, Pakistan, Sri Lanka).
- **Interpretation issues:**
  - “developing only” is ambiguous:  
    - Historically, all SAS members are/were “developing”, but World Bank now uses **income groups** (HIC/UMC/LMC/LIC) rather than “developed/developing”.
- **Options:**

  **Option A – Map to `SAS` and document approximation (simplest)**  
  - `standard_geo_code = 'SAS'`  
  - `geo_note = 'Source label: South Asia (developing only); mapped to standard South Asia region (SAS). Differences in membership/definition possible.'`  
  - Use this if you don’t need exact membership control and are comfortable with a small conceptual mismatch.

  **Option B – Define a custom aggregate code (more precise, more work)**  
  - Create a custom code, e.g. `SAS_DEV` or `SAS_DEV_ONLY`.  
  - In your **master geography table**, define:
    - `geo_code = 'SAS_DEV'`  
    - `geo_name_official = 'South Asia (developing only)'`  
    - `geo_type = 'custom_region'`  
    - `members = {list of ISO3s you consider "developing South Asia"}`  
  - Use this if:
    - The dataset you’re integrating already uses this definition consistently; or  
    - You need to reproduce exactly its regional aggregates.

If you want to stay aligned with World Bank codelists and keep things simple, **Option A (map to `SAS`) is usually acceptable**, with a clear note.

<hr>

### 4. `World (excluding high income)`

- **There is no universal, single World Bank code for “World excluding high income”.**
- **Conceptually:** This is often used as a proxy for “developing world” or “non‑high‑income countries”.
- **Common practice:**
  - Some systems define a custom aggregate like `WLD_X_HIC` or `DEV_WLD`.
- **Recommended approach:**

  **Define a custom aggregate code:**
  - `geo_code = 'WLD_EX_HIC'` (or `WLD_X_HIC`, choose a consistent naming style)  
  - `geo_name_official = 'World (excluding high income)'`  
  - `geo_type = 'custom_aggregate'`  
  - `members = {all ISO3 countries} – {all high income ISO3s}` (based on the World Bank income classification you choose for the relevant year).

- **Do NOT map this to `WLD`** (World total), because:
  - That would silently change the meaning and distort comparisons.

If your pipeline only allows standard codes, you may:

- Either extend your standard with this **one additional custom aggregate**, or  
- Exclude this series from standardized outputs and keep it in a “legacy/custom” layer.

### 5. `BGD_X`

- This looks like a **non‑standard variant around the ISO3 code**.
- Likely cases:
  - Suffix used by the source system (e.g., `_X` for “experimental”, “extended”, or similar).
- **Recommended mapping rule:**

  - If the prefix is a valid ISO3 code, **strip the suffix and map to that code**:
    - `BGD_X` → `BGD`  
  - Implementation example (regex logic):
    - Extract the first 3 letters: if they form a valid ISO3 country code in your codelist, use that.
  - In your mapping table:
    - `raw_geo_label = 'BGD_X'`  
    - `standard_geo_code = 'BGD'`  
    - `mapping_rule = 'strip_suffix_after_ISO3'`  
    - Optional `geo_note = 'Source suffix _X ignored; treated as Bangladesh (BGD).'`

- Only deviate from this if your data provider **explicitly documents** that `BGD_X` is a different geography (e.g., “Bangladesh excluding something else”). In that rare case, treat it like a custom aggregate or a separate coverage dimension.

- **Ambiguous, non‑standard region name.**
- Often used in finance/markets contexts to mean something like:

- **No direct standard World Bank code**:
  - It’s not equal to `EAS` (East Asia & Pacific)  
  - Not equal to `SAS` (South Asia)

  - `geo_type = 'custom_region'`  
  - `members = {ISO3 list explicitly defined from the data provider’s documentation}`  
- This is only safe if you can obtain or deduce a **clear country membership list** from the source.

**Option B – Exclude from standardized outputs**  
- If you cannot find a precise definition:
  - Flag `Emerging Asia` as **“unmappable to standard codes”**.
  - Either:
    - Keep it in a separate “raw/custom aggregates” table; or  
    - Drop it from your harmonized trade‑openness dataset to avoid misleading comparisons.

For a clean, World‑Bank‑aligned pipeline, **Option B is usually preferable** unless your organization already has an agreed definition for “Emerging Asia”.

CREATE TABLE geo_raw_to_standard (

    mapping_rule       TEXT,
    mapping_confidence TEXT,
    note               TEXT
);

2) Normalize labels and apply mapping in ETL

If your labels are consistent (same case/spacing), you can directly join; if not, normalize:

```sql
-- Staging: normalize raw labels
CREATE TABLE raw_trade_data_norm AS
SELECT
    LOWER(TRIM(raw_geo_label)) AS norm_geo_label,
    raw_geo_label,
    year,
    value,
    -- other fields...
FROM raw_trade_data;
```

Create a normalized mapping view/table:

```sql
CREATE TABLE geo_raw_to_standard_norm AS
SELECT
    LOWER(TRIM(raw_geo_label)) AS norm_geo_label,
    *
FROM geo_raw_to_standard;
```

Now join and keep only mapped and recognized geos:

```sql
CREATE TABLE trade_data_mapped AS
SELECT
    r.raw_geo_label,
    r.year,
    r.value,
    m.standard_geo_code AS geo_code,
    m.mapping_rule,
    m.mapping_confidence,
    m.note
FROM raw_trade_data_norm r
LEFT JOIN geo_raw_to_standard_norm m
    ON r.norm_geo_label = m.norm_geo_label
LEFT JOIN geo_standard g
    ON m.standard_geo_code = g.geo_code
WHERE
    -- keep only rows that successfully map to a known standard geo
    m.standard_geo_code IS NOT NULL
    AND g.geo_code IS NOT NULL;
```

3) Capture unmapped / ambiguous cases for review

```sql
CREATE TABLE trade_data_unmapped AS
SELECT
    r.raw_geo_label,
    r.year,
    r.value
FROM raw_trade_data_norm r
LEFT JOIN geo_raw_to_standard_norm m
    ON r.norm_geo_label = m.norm_geo_label
WHERE
    m.standard_geo_code IS NULL;
-- This will include 'Emerging Asia' and any future unknown labels
```

4) Optional: generic rule for “ISO3 + suffix” (e.g., `BGD_X`) without hard‑coding

If you want to handle patterns like `XXX_*` generically instead of mapping each:

```sql
-- Example in PostgreSQL
CREATE TABLE trade_data_mapped_generic AS
WITH base AS (
    SELECT
        raw_geo_label,
        year,
        value,
        UPPER(SUBSTRING(raw_geo_label FROM 1 FOR 3)) AS iso3_prefix
    FROM raw_trade_data
),
mapped AS (
    SELECT
        b.*,
        CASE
            WHEN s.geo_code IS NOT NULL THEN s.geo_code
            ELSE NULL
        END AS geo_code
    FROM base b
    LEFT JOIN geo_standard s
        ON b.iso3_prefix = s.geo_code
)
SELECT *
FROM mapped
WHERE geo_code IS NOT NULL;
```

You can combine this generic rule with the explicit `geo_raw_to_standard` table by:
- First applying explicit mappings via the mapping table.
- For rows still unmapped, applying the generic ISO3‑prefix rule.
